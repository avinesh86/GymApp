# Parallel PR Review

Run five reviewers (QA, security, code quality, architecture, risk) **in parallel** against a GitHub PR. Combine their findings and post **one** PR comment grouped by severity. The comment reports on every lens.

**FitOps rules this panel serves** (`CLAUDE.md`, `docs/RUNBOOK.md` §8–§9):
- Every PR gets four reviews: **Architecture, Risk, Adversarial and UI**, each by a separate agent with fresh context. This panel covers Architecture, Risk and Adversarial (the security row). **It has no UI reviewer.** If the PR changes anything a person sees (screens, error messages, emails, WhatsApp messages), run a separate UI review as well, or say in the comment that UI was not reviewed.
- Docs-only PRs need only one reviewer covering all four lenses. Releases (`test` → `main`) and back-merges (`main` → `test`) get one risk review of the whole release. Don't run the full panel on those unless asked.
- In the Reviews section, never mark a finding about security, cross-gym data, data loss or migrations as accepted. It is fixed or it goes to the owner.
- Every bug fix and feature needs tests: pytest for backend logic, Vitest for components, and Playwright (`frontend/e2e/`) for anything a person clicks through. UI tests must navigate by clicking, never `page.goto()` to an inner URL, and never call the API directly. A missing or weakened test is a finding.

## Step 1: Find the PR and fetch its inputs

- If a PR number or URL is given, use it. If not, run `gh pr view --json number,url` on the current branch. If that fails, ask which PR.
- Fetch the context **once**, into files. Some reviewer agents have no Bash and cannot fetch anything themselves.

```bash
gh pr view <N> --json number,title,body,url,baseRefName,headRefName,additions,deletions,files > /tmp/pr-<N>-meta.json
gh pr diff <N> > /tmp/pr-<N>.diff
```

- **No `gh`?** Claude Code on the web allows `gh` only for search. Use the GitHub MCP tools instead (load them with ToolSearch if they're deferred) and save their output with the Write tool to the same `/tmp` paths:
  - meta: `mcp__github__pull_request_read` with `method: "get"` (title, body, refs, additions, deletions), plus `method: "get_files"` for the file list
  - diff: `mcp__github__pull_request_read` with `method: "get_diff"`
  - to find the PR for the current branch: `mcp__github__list_pull_requests` with `head: "<owner>:<branch>"`

- **Check that the diff is complete, not truncated:**

```bash
wc -l /tmp/pr-<N>.diff
jq '.additions + .deletions' /tmp/pr-<N>-meta.json
```

  If the line count is much smaller than `additions`+`deletions`, fetch the diff again before you dispatch the agents. `frontend/package-lock.json` changes can make the real diff legitimately large. Tell the agents to skip lockfile hunks; don't fetch again. **Migrations (`apps/*/migrations/*.py`) are generated by `makemigrations`, but never skip them.** They are the main thing the risk reviewer checks.

- Reviews are better when the PR head branch is checked out, so agents can read the surrounding code. Check `git worktree list` for a checkout of `headRefName` and pass that path to the agents. If no checkout is on the head branch, do NOT switch branches. Put "diff-only review; checkout is on `<branch>`" in each agent prompt.

## Step 2: Dispatch all five agents in ONE message

Send five Agent tool calls in a single response. That is what makes them run in parallel.

The `voltagent-qa-sec` plugin is not installed in this repo. The first three rows use `general-purpose`, and each prompt must give the agent its lens explicitly ("You are the QA reviewer…").

| subagent_type | focus |
|---|---|
| `general-purpose` (QA lens) | test coverage gaps, untested edge cases, regression risk, missing validation. Check against the RUNBOOK §8 rules: a bug-fix test that would fail before the fix, Playwright for click-through flows that reaches pages by clicking (no `page.goto()` to inner URLs, no direct API calls), no weakened, skipped or deleted tests |
| `general-purpose` (security lens) | **adversarial lens**: attack the change as a hostile caller and as hostile input. Cover injection, authn/authz and IDOR for each entry point, tenant crossing (every queryset must filter by `tenant=request.tenant`; one gym must never see another's data), privilege escalation, malformed or replayed input, secrets, dependency risk. Also cover public endpoints (`public_views.py`, the WhatsApp webhook and its signature check), unsafe uploads and imports, races, timezone edge cases, and alerts sent twice |
| `general-purpose` (code-quality lens) | correctness bugs, error handling, race conditions, maintainability |
| `general-purpose` | **architecture lens**: does it fit the existing layers and patterns? Look for a second mechanism where one already exists, new coupling, a contract re-implemented for each kind of entity, and a hand-maintained list or switch with no exhaustiveness check |
| `general-purpose` | **risk lens**: blast radius in staging vs production, whether it can be rolled back, effects on data and migrations, the FitOps risk areas listed below, failures that would be silent rather than loud, and collisions with other open PRs that touch the same files |

**FitOps risk areas** (paste into the risk prompt):
- **Merging to `main` deploys automatically.** `deploy.yml` → `scripts/deploy.sh` backs up the DB, migrates, health-checks, and rolls back the **code only, never the database**. Treat any change to `scripts/deploy.sh`, `scripts/pa_deploy.sh`, `.github/workflows/`, `docker-compose.prod.yml`, `Dockerfile`, entrypoints or `nginx/` as production infrastructure.
- **Migrations:** a new required column without `db_default` breaks inserts after a code rollback. CI's `check_migration_defaults` catches that, but it can't see `RunSQL`, renamed or removed columns, edits to a migration already on `main`, or a model deleted and re-created under the same name. Also watch for locks and slow data migrations on large tables, MySQL 8 rejecting what SQLite accepts, and JSON columns on MySQL 8 (they need a hand-written migration).
- **Defaults and tenant settings** that silently change behaviour for existing gyms.
- **Celery and scheduled tasks** (`apps/*/tasks.py`, `run_scheduled_tasks`): jobs that fail silently, run twice, or send duplicate notifications.
- **Outbound messages to real people** (WhatsApp, email, in-app notifications): they can't be taken back once sent.
- **Money and payroll:** invoices, line items, approvals, payroll reports.
- **API contract:** DRF serializer shape vs `frontend/src/types/index.ts`. A mismatch fails quietly, as in the earlier "viability 0%" bug.
- **UTC vs gym-local dates:** `start_datetime.date()` returns the UTC date. Frontend filters must compare ISO `start_datetime` strings.
- **Bulk imports** (`apps/imports`): partial writes, and data landing in the wrong tenant.

Every prompt must include:
1. The paths to `/tmp/pr-<N>.diff` and `/tmp/pr-<N>-meta.json`, the PR title, and the repo root path. Tell the agent to read `CLAUDE.md` and `docs/RUNBOOK.md` §8–§9 for project rules.
2. The scope rule: **report only issues this diff introduces or directly touches.** Problems that already existed in unchanged code are out of scope.
3. The severity rubric, word for word, so all five classify the same way:
   - **Critical**: exploitable vulnerability, data loss, or breaks the main code path
   - **High**: likely bug or security weakness; fix before merge
   - **Medium**: real issue that should be fixed, but doesn't block the merge
   - **Low**: style, nice-to-have hardening, nit
4. The required output format. Agents often put analysis prose first even when told not to, so word it like this: "Your final message must BEGIN with the word FINDING (or be exactly NO FINDINGS). Everything before the first FINDING line will be discarded unread."

```
FINDING
severity: Critical|High|Medium|Low
file: path/to/file.py:123
title: <one line>
detail: <what is wrong and why it matters>
fix: <concrete recommendation>
```

An agent with nothing to report must reply exactly `NO FINDINGS`.

## Step 3: Combine the findings

- Parse the findings from all five replies.
- **Merge duplicates.** The same file:line and the same underlying issue become one entry that credits both reviewers. If they disagree on severity, use the higher one.
- **Check every cited line number yourself** before posting. Agents often get line numbers wrong. `grep -n` the quoted code in the checkout, or check it against the diff. Drop any finding whose quoted code you can't find.
- **Confirm Critical and High findings** by reading the code they point at. Don't pass on a merge-blocking claim you haven't checked.
- Order the findings Critical → High → Medium → Low and leave out empty sections.

## Step 4: Post one comment

Write the body to a file first, then post it. Never put a multi-line body inline in bash.

```bash
gh pr comment <N> --body-file /tmp/pr-<N>-review.md
```

Without `gh`, post the same body with `mcp__github__add_issue_comment` (`owner`, `repo`, `issue_number: <N>`, `body`).

Comment template:

```markdown
## 🤖 Multi-agent review panel

Reviewers: QA · Security / adversarial · Code quality · Architecture · Risk

### 🔴 Critical
- **<title>**: `path/file.py:123` _(<reviewer>; <lens>; verified|reasoned|unverified)_
  <detail>
  **Fix:** <recommendation>

### 🟠 High
### 🟡 Medium
### 🟢 Low

### Lens coverage
- **Risk:** <n findings, or "nothing found">
- **Architecture:** <n findings, or "nothing found">
- **Adversarial:** <n findings, or "nothing found">

<If a reviewer found nothing: "✅ No findings from <reviewer>.">
<If nobody found anything: a single line, "✅ No findings: all five reviewers came back clean.">

_Reviewed by a parallel agent review panel._

---
_Generated by [Claude Code](https://claude.ai/code)_
```

Show the same body in the conversation so the user sees what was posted. If the user said "dry run" or "don't post", stop before `gh pr comment` and only show the body.

## Common mistakes

| Mistake | Fix |
|---|---|
| Dispatching agents one after another | Send all five Agent calls in ONE message |
| Diff is truncated | Fetch it again and check its size against the meta JSON |
| Skipping migration files as "generated" | Skip only `package-lock.json` hunks; migrations are the risk reviewer's main input |
| Giving up because `gh` is unavailable | Use the GitHub MCP fallback in Steps 1 and 4 |
| Letting agents fetch the PR themselves | Some agents have no Bash, so fetch into /tmp files first |
| Posting a separate comment for each reviewer | Post one combined comment only |
| A reviewer's call fails and the comment goes out without its lens | Dispatch it again. If it still fails, the Lens coverage line says "not reviewed: <reason>". Never leave a lens out |
| Trusting the agents' line numbers | Check every cited line with `grep -n` before posting |
| Reporting problems that already existed | Put the scope rule in every prompt: only issues the diff introduces |
| Switching branches to review | Never touch the user's checkout; say it is a diff-only review instead |
| Treating the panel as the full RUNBOOK §9 review | It has no UI lens; add a UI review when anything a person sees changes |
